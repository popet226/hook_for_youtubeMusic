# плейлисты YouTube Music

Небольшой сервис на FastAPI. Он принимает ссылку на плейлист YouTube Music. Он возвращает данные плейлиста и треков в виде JSON.

Сервис не использует официальный YouTube Data API. Он работает без входа в аккаунт.

README разделён на практическую часть с инструкцией и исследовательскую часть с замерами, гипотезами и ограничениями.

## Практическая часть: сервис

### Как запустить

Нужен Python 3.10 или новее. Я проверял на версии 3.13.

```
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # Linux и macOS
pip install -r requirements.txt
uvicorn app.main:app
```

Сервис откроется на `http://127.0.0.1:8000`. Страница `http://127.0.0.1:8000/docs` позволяет отправить пробный запрос.

Пример запроса (PowerShell):

```
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/playlist -ContentType "application/json" -Body '{"url":"https://music.youtube.com/playlist?list=PLHHFkCbk5F28"}'
```

Тесты (подставные данные, сеть не нужна): `python -m pytest`

Скрипты в папке `research/` нужны для исследования. Сервису они не нужны. `research/check_links.py` отправляет в запущенный сервис 14 тестовых ссылок и печатает результат.

### Ручка API

`POST /playlist` с телом `{"url": "<ссылка на плейлист>"}`.

Сервис понимает такие ссылки:

- `music.youtube.com/playlist?list=…` (основная);
- `youtube.com/playlist?list=…`;
- `music.youtube.com/browse/VL…`;
- любая из них с параметрами вроде `&si=…` и `&start_radio=…`;
- автоплейлист альбома `list=OLAK5uy_…`;
- `watch?v=…&list=…` (берётся плейлист из `list`).

#### Ответ

| Поле | Что это |
| --- | --- |
| `id`, `url` | ID плейлиста и его адрес |
| `title`, `cover`, `owner` | Название, обложка (самая большая из присланных), владелец |
| `track_count` | Число треков из шапки плейлиста |
| `tracks` | Список позиций |
| `truncated` | `true`, если плейлист длиннее 30 страниц (3000 позиций) и список обрезан |

Поля позиции:

| Поле | Что это |
| --- | --- |
| `id` | ID видео |
| `title` | Название |
| `artist`, `artists` | Артисты одной строкой и списком (с ID каналов) |
| `album` | Альбом (название и ID). Для видео равно `null` |
| `duration_seconds` | Длительность в секундах |
| `cover` | Обложка |
| `kind` | `track` (аудиотрек каталога), `official_video` (официальный клип), `video` (всё остальное) |
| `video_type` | Исходное значение `musicVideoType` из ответа YouTube Music |

Если поля нет, сервис возвращает `null`. Ответ из-за этого не ломается.

Сокращённый пример:

```json
{
  "id": "PLHHFkCbk5F28",
  "url": "https://music.youtube.com/playlist?list=PLHHFkCbk5F28",
  "title": "test_playlist1",

  "owner": {"name": "ыавывап", "id": "UCtvfuq95pN7nmk1aTL5MSdQ"},
  "track_count": 24,
  "tracks": [
    {
      "id": "KwN_f0fTHoE", "title": "One Step Closer",
      "artist": "Linkin Park", "artists": [{"name": "Linkin Park", "id": "UCxgN32UVVztKAQd2HkXzBtw"}],
      "album": {"name": "Hybrid Theory", "id": "MPREb_odUae150mq3"},

      "id": "Lli99OmkPwM", "title": "Metallica - Nothing Else Matters 2007 Live Video Full HD",
```

#### Ошибки

Все ошибки имеют один вид: `{"error": {"code": "...", "message": "..."}}`.

| HTTP | `code` | Когда |
| --- | --- | --- |
| 422 | `invalid_url` | Это не ссылка |
| 422 | `unsupported_host` | Ссылка не на YouTube |
| 422 | `not_a_playlist` | Ссылка на артиста, альбом, отдельное видео |
| 422 | `mix_not_supported` | Радио или микс (`list=RD…`) |
| 404 | `playlist_not_found` | Плейлист приватный или не существует |
| 429 | `upstream_rate_limited` | YouTube Music ограничил частоту. Заголовок `Retry-After` передаётся дальше |
| 502 | `upstream_error` | Сбой сети или YouTube Music, изменилась страница |

## Исследовательская часть

### Как я выбирал способ получения данных


#### Что я попробовал

1. **Страница плейлиста (HTML).** Я скачал страницу скриптом без браузера и без аккаунта. Названия и ID треков лежат в тексте страницы. Способ работает. Страница весит 54 КБ со сжатием и 488 КБ без сжатия.
2. **Прямой запрос `browse` к внутреннему API (InnerTube).** Ключ API и версию клиента я нашёл на той же странице. Запрос `browse` работает без аккаунта. Ответ весит 21 КБ со сжатием, то есть в 2,6 раза меньше.

Я выбрал `browse`. Он легче и не требует браузера. Документации у этого API нет. Структуру ответа я разобрал сам по реальным ответам сервера.

Как это устроено в сервисе: ключ и версия клиента берутся со страницы один раз и хранятся в памяти. Одна проверка плейлиста — это один запрос `browse`. Если YouTube Music отклоняет ключ (ответ 400 или 403), сервис скачивает его заново и повторяет запрос один раз. Эту часть я проверял только на подставном сервере в тестах.

#### Какую роль оставить Data API

Это моё мнение. Оно опирается на проверенную цену в 1 единицу.

- **Проверка при добавлении плейлиста.** Один запрос на пользователя. Квота позволяет около 10 000 таких проверок в сутки.
- **Запасной путь.** Если `browse` перестанет работать, Data API даст хотя бы часть данных.
- **Грубый фильтр (гипотеза).** Метод `playlists.list` принимает несколько ID через запятую. Если он отдаёт число позиций, один запрос мог бы проверить сразу много плейлистов. Документация не называет максимум ID в запросе. Из неё также не видно, что именно считает `itemCount` и нужна ли авторизация для плейлистов «по ссылке». Если в запросе 50 ID, обход 1 000 плейлистов стоит 20 единиц. Тогда квота позволяет один обход примерно раз в 3 минуты. Это только расчёт.


#### Риски

- Внутренний API не документирован. Google может изменить формат ответа. Тогда парсер вернёт `null` в полях, которые перестали находиться. Это моё предположение, а не результат замера.
- Время жизни ключа API и версии клиента я не проверял.

### Замеры и оценка ресурсов

#### Как я измерял

- Запросы шли с одного домашнего компьютера, без аккаунта.
- Для замеров размера и времени: по 5 запросов на способ, пауза 2 секунды. Размер страницы без сжатия я отдельно измерил скриптом проверки: 488 КБ.
- Плейлист для замеров: 22 позиции (20 песен и 2 обычных видео).
- Время — от отправки запроса до чтения всего ответа. 1 КБ = 1000 байт.

#### Размер и время одной проверки

| Способ | Со сжатием | Без сжатия | Время |
| --- | --- | --- | --- |
| Страница (HTML), новое соединение | 54 КБ | 488 КБ | 0,40–0,63 с |
| `browse`, постоянное соединение | 20,7 КБ | 276 КБ | 0,12–0,17 с |

Размеры можно сравнивать напрямую. Время сравнивать нельзя: для HTML я открывал новое соединение, для `browse` использовал одно. Один запрос `browse` на новом соединении занял 0,42 с. Поэтому сервис держит одно соединение.

Стоимость одной позиции: около 0,5–0,75 КБ со сжатием. Фиксированная часть ответа: 2–5 КБ.

#### Большие плейлисты

Один ответ `browse` содержит до 100 позиций. Следующую страницу даёт токен из элемента `continuationItemRenderer`. На последней странице токена нет. Страницы нельзя запрашивать параллельно: токен приходит в предыдущей.

Плейлист с 322 позициями в шапке: 4 запроса (100 + 100 + 100 + 13 позиций), 168 КБ со сжатием, около 1 секунды (три запуска: 0,8–1,0 с).

Число в шапке (322) больше числа позиций в списке (313). То же в плейлисте, где все видео недоступны: в шапке 2, в списке 0. Я предполагаю, что недоступные видео не попадают в список, а шапка их считает. Для 9 недостающих позиций я это напрямую не проверил.

#### Ограничения и блокировки

Я проверил частоту запросов `browse` с одного адреса на одном плейлисте:

| Тест | Запросов |
| --- | --- |
| 1, 2, 5, 10 запросов в секунду по 15 секунд | 270 |
| 5 запросов в секунду, 10 минут | 3 000 |
| 20 и 50 запросов в секунду по 15 секунд | 1 050 |

Всего 4 320 запросов, около 92,5 МБ. Все ответы получили статус 200. Медиана времени 0,12 с, 95-й процентиль 0,14–0,16 с, размер ответа около 21,4 КБ. Ошибок 429 и 403, капч и сетевых ошибок не было.

Предел я не нашёл. Из этого нельзя делать вывод, что предела нет: тесты короткие, адрес один, плейлист один.

#### Как понять, что плейлист изменился

Для этого я сохраняю список ID позиций и число из шапки (`research/snapshot_diff.py`). Тест на малом плейлисте:

| Что сделал | Число в шапке | Позиций | Результат сравнения |
| --- | --- | --- | --- |
| Первый снимок | 22 | 22 | — |
| Добавил песню | 23 | 23 | новая позиция 23 из 23 |
| Добавил обычное видео | 24 | 24 | новая позиция 24 из 24 |
| Удалил позицию | 23 | 23 | удалена позиция 8 из 24 |

Выводы:

- Число в шапке меняется сразу. Песни и обычные видео считаются одинаково.
- Новые позиции попали в конец списка (три раза подряд, настройки по умолчанию).
- Для плейлиста до 100 позиций первая страница содержит всё: можно сравнить весь список. Для длинного плейлиста можно сначала сравнить число из шапки и, если оно изменилось, пройти остальные страницы. Для плейлиста на 322 позиции это 1 запрос вместо 4.
- Слабое место: если между проверками одну позицию добавили, а другую удалили, число не изменится. Длинный плейлист пропустит такое изменение. Смягчить можно редкой полной проверкой. Эту идею я не проверял.

Сервис сейчас всегда загружает плейлист целиком. Сравнение со снимком должен делать feed updater.

#### Нагрузка на 1 000 пользователей

Это расчёт по моим замерам.

| Режим | Что проверяем | Запросов в секунду | Трафик в секунду | Трафик в сутки |
| --- | --- | --- | --- | --- |
| Раз в 60 с | малый плейлист (21 КБ) | около 17 | 0,35 МБ | около 30 ГБ |
| Раз в 20 с | малый плейлист (21 КБ) | 50 | 1,0 МБ | около 89 ГБ |
| Раз в 60 с | 322 позиции целиком (168 КБ, 4 запроса) | около 67 | 2,8 МБ | около 242 ГБ |
| Раз в 20 с | 322 позиции целиком | 200 | 8,4 МБ | около 725 ГБ |
| Раз в 20 с | 322 позиции, только первая страница (54,5 КБ) | 50 | 2,7 МБ | около 235 ГБ |

Формулы: запросов в секунду = пользователи / интервал × число страниц; трафик в сутки = запросов в секунду × размер ответа × 86 400.

Строки про 322 позиции — худший случай: все 1 000 пользователей с таким плейлистом. Реальное распределение размеров я не знаю.

#### Где предел и что бы я изменил

Подтверждённый максимум: 50 запросов в секунду в течение 15 секунд и 5 запросов в секунду в течение 10 минут. Это покрывает режим «1 000 пользователей раз в 20 секунд» для плейлистов до 100 позиций, но только на 15 секунд. Длительную работу на такой частоте я не проверял.

Что я бы изменил:

- проверять первую страницу, а остальные только при изменении числа;
- распределять проверки равномерно по времени, а не залпом раз в 20 секунд;
- реже проверять плейлисты, которые давно не менялись;
- при ответе 429 ждать время из `Retry-After`;
- если начнутся блокировки, распределить запросы по нескольким адресам.

Первое решение требует работы feed updater.

#### Дом и дата-центр

Все замеры сделаны с домашнего компьютера без VPN. Замеров с сервера в дата-центре нет. Не знаю, отличается ли поведение.

### Допущения

- Плейлисты публичные или доступны по ссылке. Авторизации нет.
- Язык запросов к API: английский (`hl=en`).
- Тип позиции берётся из `musicVideoType`. В моих данных встретились `ATV`, `OMV`, `OFFICIAL_SOURCE_MUSIC`, `UGC` и `PODCAST_EPISODE`. Аудиотреком каталога (`track`) считается только `ATV`. Клипы `OMV` и `OFFICIAL_SOURCE_MUSIC` получают `official_video`. Всё остальное, включая неизвестные типы, получает `video`. Исходное значение всегда видно в `video_type`.
- У обычных видео нет альбома. В поле артиста у них стоит название канала.
- В третьей колонке не всегда альбом (у одного видео там была дата). Альбомом считается часть, у которой ID начинается с `MPRE`.
- Год релиза не возвращается. В записи списка его нет. Отдельный запрос на каждый трек был бы слишком дорогим.
- `track_count` — число из шапки. Оно может быть больше длины `tracks`. Если шапки нет (автоплейлист альбома), сервис возвращает длину списка. Если список обрезан, возвращается `null`.
- Недоступные видео в список не попадают.
- Радио и миксы (`list=RD…`) сервис не принимает. Это автоматический список, он строится по выбранному треку и меняется сам. Исключение: `RDCLAK5uy_…` — подборки самого YouTube Music, сервис их принимает. Ответ на такую ссылку я не проверял.
- Приватный плейлист и несуществующий плейлист выглядят одинаково (ответ без шапки и без списка). Сервис возвращает 404 в обоих случаях.
- Таймаут запроса к YouTube Music: 15 секунд. Повторных попыток при ошибках 5xx нет: сервис возвращает 502.
- Максимум 30 страниц (3 000 позиций) на плейлист.

### Что я не проверил

- Блокировки при длительной нагрузке (час и больше), с других адресов, с сервера в дата-центре.
- Нагрузку на много разных плейлистов (мои тесты шли на один).
- Время жизни ключа API и версии клиента.
- Обновление ключа при реальном отказе (проверено только в тестах на подставном сервере).
- Замену одной позиции другой между проверками, добавление в начало списка, повторное добавление одной позиции.
- Данные шапки автоплейлиста альбома.
- Идею про Data API как грубый фильтр.
